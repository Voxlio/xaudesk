## Phase 2 — Findings

### CRITICAL

#### C1 — News caching is inert; the `NewsCache` table is never written, so the documented fallback can never fire

`data/news/index.ts:78` — `store: options.store ?? new MemoryNewsCacheStore()`.
`getNewsAdapter()` is called with no `store` at `strategy/service.ts:51`, `:85` and `:130`, and each call constructs a **brand-new adapter with a brand-new empty in-memory store**. `createPrismaNewsStore` (`data/news/index.ts:89`) is exported but never called anywhere in application code, and the `NewsCache` model (`prisma/schema.prisma:75`) is never read or written.

Why it's a problem. The 30-minute fresh-cache short-circuit (`forexFactory.ts:93`) can never hit, so every idea generation re-fetches the feed two or three times over the network. More seriously, the stale-cache (`:127`) and newest-cache (`:137`) fallbacks are always empty, so **a feed outage lands straight on `origin: 'empty'` with `events: []`** (`:148`). CLAUDE.md requires "Cache it and fail gracefully": the graceful-failure machinery is well written, but the cache that powers it is never populated.

Proposed fix. Build the store once at module scope via `createPrismaNewsStore(prisma)` and memoise the adapter instance so a process reuses one cache.

#### C2 — A news-feed outage silently disables the 30-minute blackout

`strategy/index.ts` — `const events = await safely(() => options.news.fetchThisWeek(), []);`

On failure `events` is `[]`. `blackoutStatus([], at)` then reports **not blocked** (`strategy/blackout.ts`; `isTradeBlocked` returns false on an empty calendar unless `failClosed: true`, which is never set anywhere). So when the calendar is unavailable, the hard rule "No trades 30 min around high-impact news" is quietly switched off — and because the macro inputs can still be present, the idea stays directional and tradeable. Combined with C1 there is no cache to fall back on, so this is reachable on any single feed hiccup.

Proposed fix. Thread the fetch outcome through to `blackoutStatus` and fail **closed**: no calendar means no trade, stated in `reason`. The `failClosed: true` option already exists for exactly this.

### HIGH

#### H1 — The stop loss can be placed inside the quoted entry zone

`strategy/tradeIdea.ts:204-215` together with `findStructuralStop`.

The zone is `[close − halfZone, close + halfZone]` where `halfZone = max(atr * 0.05, 0.01)`, but `findStructuralStop` only rejects a candidate on the wrong side of **`entry.price`, the M15 close** — never against the zone edges. For a BUY, a latest H1 swing low in `(close + 0.05·atr, close + 0.1·atr)` gives `candidate = swingLow − 0.1·atr`, which lands in `(entryLow, close)` and is accepted. `stopDistance = entryHigh − stopLoss` is still positive, so the `:213` guard passes and the idea ships with a stop **above `entryLow`**. Filling at the better edge of your own entry zone would put you instantly past your stop, and most brokers would reject the order outright.

Proposed fix. After rounding, assert `stopLoss < entryLow` for BUY and `stopLoss > entryHigh` for SELL, returning No-Trade otherwise; pass the zone edge rather than the close into `findStructuralStop`.

#### H2 — Recorded R-multiples are wrong by one R on every win

`lib/tradeOutcomes.ts:48` — `rMultiple: ... Number(hit.result.slice(2))`, so "TP1" → 1, "TP2" → 2, "TP3" → 3. But the ladder is 2R/3R/4R (`strategy/tradeIdea.ts:237-239`, labelled as such in `app/page.tsx:140-142`). A TP1 win is therefore logged as **+1R when it was +2R**, and every performance figure derived from `rMultiple` is understated by a full R.

Proposed fix. Compute it from prices — `(exit − entry) * sign / stopDistance` — or persist the planned R for each target on the idea.

#### H3 — TP2 and TP3 are unreachable in the outcome tracker, so the ladder is fiction

`lib/outcomes.ts:18-23` and `:26-31` — within each candle the targets are scanned in order and the function **returns on the first hit**. Price must clear TP1 before TP2, so TP1 always wins and the trade closes there. TP2 and TP3 can only ever be recorded if a single candle skips TP1 entirely, which cannot happen for a monotone ladder. Combined with H2, every win in the track record is logged as TP1 at +1R.

Proposed fix. Decide and document the convention — full close at TP1, scaled partials, or "furthest level reached" — then implement it and make `TradeOutcome.result` reflect it.

#### H4 — Ideas older than the outcome window are evaluated against the wrong bars

`lib/tradeOutcomes.ts:14` fetches a single H1 window of 1000 bars (about 41 days) and reuses it for every open idea; `:36` filters `candle.time > since`. For an idea older than that window the filter keeps the **entire** window, whose first bar is roughly 41 days *after* the idea was generated. The outcome is then computed from unrelated price action and written as a WIN or LOSS.

There is also no expiry: an un-hit idea stays `OPEN` indefinitely and is re-evaluated against each new day's bars until something eventually touches a level.

Proposed fix. Skip or mark INDETERMINATE when `since < candles[0].time`, and add an explicit expiry (for example void after five trading days) with its own status.

#### H5 — The backtest does not test the strategy the app publishes

`backtest/engine.ts` — `signalAt()` is an H4 EMA 50/200 plus RSI-50-cross baseline with a 1.5·ATR stop. It never calls `strategy/tradeIdea.ts`: no three-confluence gate, no supply/demand, liquidity-sweep or BOS-pullback checks, no fundamental bias, **no news blackout**. It also bypasses `calculateCentLots` entirely — sizing is continuous `ounces` with no lot step, no minimum, no maximum and no margin check. The resulting equity curve cannot be reproduced by the real cent account.

To its credit `app/api/backtest/route.ts:47` discloses this in `assumptions.strategy`, but the numbers are still presented on `/backtest` as the system's track record.

Proposed fix. Either drive the backtest through `createTradeIdea` and `calculateCentLots` over real historical candles and calendar data, or label the page unambiguously as a baseline benchmark and list the omitted filters.

#### H6 — `PUT /api/settings` is unauthenticated

`app/api/settings/route.ts:29` has no authentication of any kind. Anyone who can reach the deployment can rewrite `equityUsd`, `riskPercent`, `centLotStep` and `centLotMin` — the inputs that directly drive published lot sizes. `vercel.json` shows this is intended for deployment, so this would be internet-exposed. The input *validation* is good (`:37-48`); it is only the authorization that is missing.

Proposed fix. Require the same bearer secret as the cron routes, or a session.

#### H7 — Public, unauthenticated, unrate-limited endpoints burn the upstream quota

`/api/candles` makes one Twelve Data call per request (up to 1000 bars), `/api/backtest` fetches 5000 H4 bars per request with no caching, `/api/history` makes one H1 call plus N database upserts per request, and `/api/idea` can trigger full generation. The Twelve Data free tier is 8 requests/minute and 800/day (noted in `data/price/twelveData.ts:13`). A handful of requests exhausts the daily quota and takes the daily idea offline. There is no rate limiting anywhere in the repo.

Proposed fix. Rate-limit the data-fetching routes, cache `/api/backtest` output (the `CandleCache` model already exists and is unused — see L7), and require auth for anything that triggers an upstream call.

#### H8 — `GET /api/history` performs writes

`app/api/history/route.ts:7` calls `refreshTradeOutcomes()`, which upserts a `TradeOutcome` per idea (`lib/tradeOutcomes.ts:21` and `:51`). A GET mutates state, is unauthenticated, and fires on ordinary page navigation — N+1 writes growing with history, on every page view.

Proposed fix. Make GET read-only from the database and leave mutation to `/api/cron/outcomes`.

### MEDIUM

#### M1 — Non-deterministic `unavailable` ordering (real bug, causes a test failure)

`data/macro/live.ts:41-45` — one `unavailable` array is mutated by two concurrently-awaited functions. `readUs10y` pushes synchronously when `this.fred === null`, before `readUsdProxy` resumes past its `await`, so the array order depends on interleaving. `tests/data/macro.test.ts:144` expects `['USD_PROXY','US10Y']` and receives `['US10Y','USD_PROXY']`.

Proposed fix. Have each reader return its own issues and concatenate them in a fixed order after `Promise.all`.

#### M2 — Requested percent change does not round-trip (real bug, causes a test failure)

`data/macro/fixture.ts:56-57` and `:149` — `changeAbsolute = last * (pct/100)` is percent *of last*, but `reading()` computes `changePercent = (changeAbsolute / |reference|) * 100`, percent *of reference*. Requesting 0.4 returns 0.4016064257028112. The test's own helper has the correct inversion: `reference = last / (1 + pct/100)`.

Proposed fix. Derive `reference` from the requested percent the way the test does.

#### M3 — Test bug in the macro suite

`tests/data/macro.test.ts:131` asserts `snapshot.us10y?.symbol === 'DTWEXBGS'`. The 10-year yield series is `DGS10`; DTWEXBGS is the dollar index used as the *UUP fallback*. Line 133's `fred.calls[0]` assertion is additionally order-dependent on M1.

Proposed fix. Expect `DGS10`, and select the FRED call by series id rather than by index.

#### M4 — Dead-band applied to the normalized value rather than the raw input — **needs your decision**

`strategy/fundamental.ts:364` — `components.filter(item => Math.abs(item.value) > 0.05 && ...)` runs on the already-normalized component. A −0.04% UUP drift normalizes to −0.08, clears the 0.05 band, and is counted as disagreement, giving confidence 50. `tests/strategy/fundamental.test.ts:445` ("does not treat noise as disagreement") expects 80.

I am flagging this rather than guessing. Which is authoritative: is the dead-band meant to be in raw input units, so the code should compare before normalizing and the test is right? Or in normalized units, so the test's expectation should change?

#### M5 — Confidence is partly unexplained and is published on No-Trade ideas

`strategy/tradeIdea.ts:132` — `round((passed/evidence) * 50 + fundamentals.confidence * 0.5)`.

Three problems. `fundamentals.confidence` is coverage × agreement, which is *data availability*, not conviction — so the magnitude of `usdScore` never reaches the number, and a strong read on thin data scores low. The arithmetic is never stated in `reason` (the string explains the inputs at `:168-173` but not this formula), which is precisely what CLAUDE.md's "no black-box logic" rule targets. And `confidence` sits in `base` at `:156`, so it is attached to every NO_TRADE idea and `app/page.tsx:174` renders it unconditionally — a rejected setup can display "72/100".

Proposed fix. Show the terms in `reason`, and set confidence to 0 (or omit it) on NO_TRADE.

#### M6 — No maximum lot cap, and no margin or leverage check

`risk/index.ts` defines `DEFAULT_CENT_LOT_STEP` and `DEFAULT_MIN_CENT_LOT` but **no maximum**. A tight stop produces an arbitrarily large position: at a $0.05/oz stop distance with $1,000 equity at 2%, that is 400 cent lots, with nothing checking whether the account can margin it. `strategy/tradeIdea.ts` also derives `stopDistance` from a possibly-zero ATR (`latest(atr(...)) ?? 0` on short history), which makes a tiny stop distance reachable.

Proposed fix. Add `maximumLot` and a required-margin estimate to `calculateCentLots`, reject above the cap, and add tests.

#### M7 — Position-value math re-implemented outside `/risk`

`lib/tradeOutcomes.ts:40` — `(hit.price − entryPrice) * sign * idea.lotSize` is only correct because `OUNCES_PER_CENT_LOT === 1`. That coincidence is hardcoded rather than imported, so changing `CENT_LOT_DIVISOR` would silently corrupt every P&L figure. It also ignores spread and slippage, so the tracked record flatters reality.

Proposed fix. Import `OUNCES_PER_CENT_LOT` from `risk/index.ts` and apply the same exit fee the backtest uses.

#### M8 — One malformed provider bar fails the whole day

`data/price/twelveData.ts:150` uses `normalizeCandlesStrict`, i.e. `onInvalid: 'throw'`. A single bar with `high < low` or a zero price aborts idea generation and produces a price-unavailable No-Trade.

Proposed fix. Use `onInvalid: 'drop'` on the live path and surface the dropped count as a snapshot warning.

#### M9 — `npm run lint` is not configured

`next lint` prompts interactively; there is no ESLint config in the repo and `eslint` is not a dependency. The script is unusable locally and would hang in CI.

Proposed fix. Add `eslint` and `eslint-config-next` with a checked-in config, or remove the script.

#### M10 — No lockfile

There is no `package-lock.json`, and every dependency is caret-ranged. Two installs can resolve to different trees, which is not acceptable for a system whose output is numeric.

Proposed fix. Commit a lockfile and use `npm ci`.

#### M11 — No migrations

`prisma/migrations/` does not exist; the workflow is `db:push` only. There is no schema history, so production changes are unversioned drift.

Proposed fix. Move to `prisma migrate dev` locally and `prisma migrate deploy` in the pipeline.

#### M12 — Backtest omits commission and swap, and duplicates its own assumptions

`backtest/engine.ts` models `spreadDollars / 2 + slippageDollars` (defaults 0.30 and 0.10) but no commission and no overnight financing, for a strategy that holds positions across days. `app/api/backtest/route.ts:42-48` then restates `initialBalanceUsd: 100`, `riskPercent: 1`, `spreadDollars: 0.3`, `slippageDollars: 0.1` as literals duplicating the engine defaults — they will drift apart — and it ignores the user's configured equity and risk entirely.

Proposed fix. Add commission and swap inputs; read the assumptions back out of the engine and from settings.

#### M13 — ISO week key versus ForexFactory's Sunday-start week

`data/news/parse.ts:213` keys the cache by ISO week, which starts Monday. The `ff_calendar_thisweek.json` feed rolls over on **Sunday**. A Saturday payload and the following Sunday's payload therefore describe different sets of events but share one cache key. Harmless today only because C1 means nothing is ever cached; it becomes a wrong-week fallback as soon as caching is fixed.

Proposed fix. Key on the feed's own Sunday-start week boundary.

#### M14 — A naive feed timestamp would be read as UTC, shifting every event four to five hours

`data/normalize.ts:102-104` appends `Z` when no offset is present. The ForexFactory feed currently stamps an explicit US-Eastern offset, which is honoured correctly — so DST is right today. But if the feed ever emits naive local times, the whole blackout window moves by a session with no error raised.

Proposed fix. For news timestamps, require an explicit offset or default to `America/New_York`, and warn.

#### M15 — The prior idea row is deleted rather than superseded

`strategy/service.ts:48` — on synthetic data, a price-source change or a price-unavailable retry, the day's row is `delete`d and regenerated. That destroys the audit trail CLAUDE.md asks for ("so an idea can always be audited after the fact", `prisma/schema.prisma:36`) and permits a second, different idea for the same calendar day, which is the exact thing the `@unique` on `tradeDate` exists to prevent. It also cascades the `TradeOutcome` away (`schema.prisma:53`).

Proposed fix. Supersede rather than delete — add a `supersededAt` or revision column — or update in place.

#### M16 — Unguarded await in the cached-idea branch

`strategy/service.ts:51` — `await getNewsAdapter().fetchThisWeek()` sits outside any try/catch. `ForexFactoryAdapter.fetchThisWeek` is documented never to throw, but the *adapter resolution* above it can (`data/news/index.ts:67` throws on an unknown `NEWS_ADAPTER`), which would 503 a request that already had a perfectly good cached idea.

Proposed fix. Wrap it and fall back to returning the cached idea.

#### M17 — `riskPercent` bounds are inconsistent across layers

`risk/index.ts` hard-rejects anything outside 1–2%. `app/api/settings/route.ts:40` correctly enforces 1–2. But `strategy/service.ts:91` reads the environment variable through `parsePositive` with no range check, so `ACCOUNT_RISK_PERCENT=5` surfaces as a confusing "risk inputs are invalid" No-Trade (`tradeIdea.ts:228`). `backtest/engine.ts` accepts 0–100.

Proposed fix. Validate and clamp at the environment boundary with a clear message, and either align the backtest's bound or document why it differs.

#### M18 — Indicator tests lack non-finite and causality coverage

`indicators/*.ts` has no guards against `NaN` or `Infinity` (a NaN high silently yields no swing pivots in `structure.ts`), and nothing tests the property the entire backtest depends on: that appending later bars never changes an earlier value. The existing reference values are hand-derived and well documented (`tests/indicators/rsi.test.ts:4-22` works the whole Wilder series out by hand), but they are all self-generated — none is cross-checked against a published Wilder table or a platform value, so a shared misunderstanding of a formula would be invisible.

Proposed fix. Add non-finite input tests, a prefix-stability (causality) test per indicator, and at least one third-party reference value.

#### M19 — Risk tests cover only four cases

`tests/risk/centLots.test.ts` has no non-default `lotStep` or `minimumLot` case, no maximum-lot case (there is no feature), no `riskPercent` boundary cases at exactly 1 and 2, no non-finite `stopDistanceUsdPerOunce`, and nothing covering L1.

Proposed fix. Extend these alongside any lot-math change.

#### M20 — HFM contract-spec assumptions are unverified — **needs your confirmation**

`risk/index.ts` and `.env.example:35-37` assume all of the following. I will not guess at any of them:

- `STANDARD_LOT_OUNCES = 100`
- cent divisor 100, therefore **1 cent lot = 1 ounce**
- minimum cent lot 0.01
- cent lot step 0.01
- **no maximum lot**
- gold quoted to 2 decimals (`round(..., 2)` throughout `tradeIdea.ts`)

Please confirm each against the XAUUSD symbol specification in your HFM Cent account, along with the leverage and margin requirement and whether HFM charges commission on gold. The "1 cent lot = 1 ounce" identity is what makes `lib/tradeOutcomes.ts:40` accidentally correct and is what the entire displayed risk math rests on.

### LOW

**L1 — `decimalPlaces` breaks on exponential notation.** `risk/index.ts`: `String(1e-7)` is `"1e-7"` with no `"."`, so a very small `lotStep` yields zero decimal places and `toFixed(0)` rounds the lot to a whole number. Not reachable with the 0.01 default, but `lotStep` is user-configurable through `/api/settings` and `ACCOUNT_CENT_LOT_STEP`.

**L2 — `Number.EPSILON` used as an absolute tolerance.** `risk/index.ts`: `Math.floor((rawCentLots + Number.EPSILON) / lotStep)`. `Number.EPSILON` is about 2.2e-16, meaningful only near 1.0; for `rawCentLots` in the hundreds the guard does nothing. Use a relative tolerance.

**L3 — The "2R / 3R / 4R" labels are hardcoded in the view.** `app/page.tsx:140-142` duplicates the ladder defined at `strategy/tradeIdea.ts:237-239`. Derive them instead.

**L4 — `app/api/candles/route.ts:73` rethrows** non-`PriceAdapterError` causes, producing a framework 500 while every sibling route returns a JSON 503. Inconsistent for clients.

**L5 — Raw error messages reach users.** `app/page.tsx:92` renders the exception message, and every route returns `cause.message`. Prisma errors include the database file path. No API key is exposed — I checked specifically: the key appears only in query strings (`twelveData.ts:95`, `fred.ts:41`), is never interpolated into a message, and there is no logging anywhere in the repo that could print a URL. Still worth a generic message in production.

**L6 — `TwelveDataAdapter` leaves `fetch` unbound.** `twelveData.ts:71` uses `globalThis.fetch` directly where `ForexFactoryAdapter` binds it (`forexFactory.ts:71`). Works under Node; the inconsistency is the point.

**L7 — `CandleCache` is dead schema.** `prisma/schema.prisma:86` is never read or written — and it is exactly the cache `/api/backtest` needs for H7.

**L8 — Backtest equity curve discontinuity.** `backtest/engine.ts` resets `balance` to `initialBalance` for the out-of-sample segment, so the curve breaks across the split, and it pushes two equity points at `startIndex`. Separately, `winRate` counts a breakeven trade as a loss while `grossLoss` excludes it.

**L9 — ATR computed twice.** `indicators/index.ts:78-79` calls `atr` and then `atrPercent`, which recomputes ATR internally.

**L10 — No container, and SQLite will not persist on the documented target.** There is no Dockerfile or compose file. `DATABASE_URL` defaults to `file:./prisma/dev.db` (`.env.example:28`) — a path inside the deployment, and on Vercel (per `vercel.json`) that filesystem is ephemeral and read-only, so the database will not survive.
